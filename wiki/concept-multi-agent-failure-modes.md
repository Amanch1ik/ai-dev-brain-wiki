# Режимы отказа мультиагентных систем

Почему связка из нескольких LLM-агентов ломается чаще, чем один агент, и какие именно отказы измерены эмпирически. Читать до того, как строить оркестрацию — большинство провалов организационные, а не «модель тупая».

## Содержание

### Позиция Cognition: «Don't Build Multi-Agents»

Walden Yan (Cognition, июнь 2025) сформулировал два принципа, из которых выводится почти вся практика:

1. **Share context — и делись полными трейсами, а не отдельными сообщениями.** Передать воркеру «исходную задачу» недостаточно: реальная постановка живёт в многоходовом диалоге, tool calls, уточнениях и отвергнутых вариантах. Кто не видел трейс — интерпретирует задачу иначе.
2. **Actions carry implicit decisions, and conflicting decisions carry bad results.** Каждое действие агента молча фиксирует решение (стиль, архитектура, нейминг, обработка edge-case). Два агента, действующих параллельно, принимают эти решения независимо → результаты не стыкуются **по вкусу, а не по интерфейсу** — и это не ловится тестами.

**Канонический пример (Flappy Bird).** Оркестратор дробит задачу на два сабтаска. Воркер A рисует фон — и делает его в стиле Super Mario Bros. Воркер B рисует птицу в другой стилистике. Агент-интегратор получает два несовместимых артефакта и **не может их спасти**: расхождение уже вшито в результаты, а миссинтерпретация случилась на этапе декомпозиции, которого интегратор не видел. Проблема не в интеграции, а в том, что чинить дороже, чем переделать.

Рекомендованная тогда архитектура: **single-threaded linear agent** (один непрерывный контекст) плюс, при упоре в [[concept-context-window]], **context-compression model** — отдельная LLM, дистиллирующая историю в ключевые решения. Авторы честно пишут, что компрессор *hard to get right* и может требовать доменного файнтюна.

Тогда же они разобрали чужие системы: **сабагенты Claude Code** названы «правильным» примером — они **не параллелят работу по подзадачам, а отвечают на вопросы**, и у них нет контекста, чтобы принимать самостоятельные кодовые решения. **OpenAI Swarm и Microsoft AutoGen** — наоборот, названы продвигающими неверный способ строить агентов.

### Ревизия Cognition (апрель 2026): что реально заработало

Позиция смягчена, но не отменена. Формула: *multi-agent systems work best today when writes stay single-threaded and the additional agents contribute **intelligence rather than actions***.

Три паттерна, которые у них работают:

- **Code-Review-Loop** — отдельный ревьюер смотрит на код кодящего агента. Выигрыш даёт **clean context advantage** (ревьюер не страдает от context rot, накопленного за часы работы) и свежая перспектива. Кодящий агент **фильтрует** фидбек через исходные инструкции пользователя — это защита от scope creep и бесконечного цикла.
  ⚠ Контринтуитивный поворот: здесь агенты **не должны** делиться контекстом заранее — прямо против Принципа 1. То есть **Принцип 1 применим к разделяемой работе и вреден для независимой верификации**. Ключевой нюанс для дирижёра.
- **Smart Friend** — быстрая модель делегирует «умному другу», когда упирается. Работает, только если **обе модели frontier-tier** (тогда это фактически capability router). При асимметрии ломается: слабая модель не умеет распознать свой предел, корректно ограничить вопрос и извлечь пользу из ответа.
- **Map-Reduce-and-Manage** — менеджер режет крупную работу, порождает исполнителей, синтезирует. Масштабируется за пределы одного PR, но менеджеры без глубокого знания кодовой базы становятся *overly prescriptive*.

По-прежнему **не работает**: parallel-writer swarms (фрагментация решений не лечится ростом моделей), неструктурированные peer-to-peer рои («mostly a distraction»), асимметричные пары моделей.

⚠ проверить: цифры «~2 бага на PR, ~58% из них severe» и «рост использования Devin ~8x за полгода» взяты из их поста через саммари, глазами не сверены.

### Контрпозиция Anthropic: на research мультиагент выигрывает

На **другом классе задач** вывод противоположный. Claude Opus 4 как lead + Sonnet 4 как сабагенты дали **+90,2%** относительно одиночного Opus 4 на внутреннем research-eval (breadth-first запросы вроде «собрать всех членов советов директоров компаний S&P 500 IT»).

Трезвящий факт оттуда же: **token usage сам по себе объясняет 80% вариации** результата на BrowseComp; остальное — выбор модели и число tool calls. То есть значительная часть «магии мультиагента» — это просто **больше потраченного compute**, а не координация. Цена: мультиагент жрёт **~15× токенов** обычного чата, одиночный агент — ~4× (см. [[method-token-economy]]).

Где мультиагент не работает — их собственными словами: **кодинг** («меньше по-настоящему параллелизуемых задач, чем в research»), домены с общим разделяемым контекстом, задачи с сильными взаимозависимостями. И: «LLM-агенты пока плохо координируются и делегируют в реальном времени».

### Примирение: спор идёт о разных задачах

| | Cognition (кодинг) | Anthropic (research) |
|---|---|---|
| Природа задачи | Писать **один когерентный артефакт** | Собрать **множество независимых фактов** |
| Ошибка воркера | Конфликтует с чужой работой | Просто отсутствующий/лишний факт |
| Нужен общий вкус/стиль | Да | Нет |
| Слияние результатов | Нетривиально, часто невозможно | Тривиально (union / dedup) |
| Вердикт | Single-threaded **writes** | Fan-out **reads** |

**Главное правило: разделяй по оси «write vs read», а не по оси «сложно / просто».** Рабочее решающее правило — в [[method-agent-orchestration]].

### MAST — эмпирическая таксономия отказов

«Why Do Multi-Agent LLM Systems Fail?» (Cemri, Pan, Yang, … Zaharia, Gonzalez, Stoica; Berkeley, NeurIPS 2025) — первая эмпирическая таксономия. Метод: 150 трейсов размечены экспертами (**κ = 0,88** между аннотаторами), затем LLM-as-judge пайплайн масштабировал разметку до **1600+ трейсов, 7 фреймворков, 4 семейства моделей**. Наблюдаемые failure rates по фреймворкам: **41%–86,7%**.

**14 режимов в трёх категориях:**

**FC1. System Design / Specification — 41,8%**
- FM-1.1 Disobey task specification — 11,8%
- FM-1.2 Disobey role specification — 1,5%
- FM-1.3 **Step repetition — 15,7%**
- FM-1.4 Loss of conversation history — 2,8%
- FM-1.5 **Unaware of termination conditions — 12,4%**

**FC2. Inter-Agent Misalignment — 31,4%**
- FM-2.1 Conversation reset — 2,2%
- FM-2.2 Fail to ask for clarification — 6,8%
- FM-2.3 Task derailment — 7,4%
- FM-2.4 Information withholding — 0,85%
- FM-2.5 Ignored other agent's input — 1,9%
- FM-2.6 **Reasoning-action mismatch — 13,2%**

**FC3. Task Verification — 23,5%**
- FM-3.1 Premature termination — 6,2%
- FM-3.2 No or incomplete verification — 8,2%
- FM-3.3 Incorrect verification — 9,1%

**Вывод:** отказы преимущественно **организационные** — дефекты спецификации, координации и верификации, то есть зона ответственности дирижёра, а не модели. Case study на ChatDev: улучшение role specification дало **+9,4%** success, добавление верификации высокоуровневой цели — **+15,6%** на ProgramDev **при тех же моделях**. Но авторы подчёркивают: значительная часть отказов не лечится поверхностными правками промпта и требует архитектурных решений.

Практический вывод: три самых частых мода (step repetition, reasoning-action mismatch, unaware of termination) лечатся одними и теми же полями брифа — **явный критерий остановки**, требование действовать по собственному выводу, и доступ к списку уже сделанного.

⚠ проверить: частоты по отдельным FM брались из HTML-версии v3 через саммари.

### Недоспецифицированный бриф делает воркера нестабильным

«LLMs Get Lost In Multi-Turn Conversation» (Microsoft/Salesforce, 200k+ симулированных диалогов): при **недоспецифицированной** постановке падение **~39%** относительно однооборотной формулировки. Разложение важнее самой цифры: аптитьюд теряется на ~16%, а **unreliability растёт на ~112%** — разброс между лучшим и худшим прогоном одной и той же инструкции доходит до 50 п.п. Причина: модель делает допущения в ранних тёрнах, преждевременно фиксирует решение и **не восстанавливается**, свернув не туда.

Для оркестратора это буквально означает: **плохой бриф не просто ухудшает результат, он делает его нестабильным**, а нестабильность не чинится ретраем — только переформулировкой.

### Гомогенная панель, которая совещается, — антипаттерн

- **«Debate or Vote»** (7 бенчмарков; Qwen2.5-7B/32B, Llama3.1-8B; N=5 агентов): на Qwen2.5-7B single-agent 72,05% → **majority voting 76,91%** → decentralized multi-agent debate 73,77%. Теоретическая часть моделирует дебаты как **мартингейл** над траекториями убеждений: ожидаемое убеждение на следующем раунде равно текущему, значит дебаты сами по себе **не повышают ожидаемую корректность**, только добавляют стохастику. Что-то дают только при **разных персонах/ролях**.
- **«The Cost of Consensus»** (10 идентичных агентов, 3 раунда): изолированная само-коррекция ≥ дебатов (MMLU-Hard Qwen: **66,7% self-correction против 60,7% debate**), дебаты стоят **2,1–3,4× токенов**, **сикофантия до 85,5%** (агент бросает верный ответ ради большинства), **oracle gap до 32,3 п.п.** — правильный ответ был в пуле в 74,3% случаев, но голосование его выбросило.
  ⚠ Модели 7–8B; на frontier-моделях может быть иначе, авторы сами ограничивают вывод этим классом.

Работает вместо этого: независимые прогоны + агрегация, **гетерогенные** линзы вместо одинаковых судей, асимметричные роли (генератор ≠ критик).

### Смещения LLM-as-judge

- **Position bias** — предпочтение позиции в промпте; лечится дёшево перестановкой порядка вариантов и усреднением.
- **Verbosity bias** — длинное кажется лучше.
- **Self-preference bias** — модель переоценивает собственные выходы. Смягчение: **cross-family judging** (судья из другого семейства, чем генератор) и **ensemble judges**.

### Сводная таблица отказов

| Отказ | Конкретика из источников | Противоядие |
|---|---|---|
| Дублирование работы | Vague brief «research the semiconductor shortage» → одинаковые поиски у разных воркеров | Non-overlap statement в брифе |
| Конфликтующие правки | Flappy Bird: несовместимые артефакты, интегратор бессилен | **Single writer**; параллелить только чтение |
| Выход за scope | Ревьюер генерит бесконечные предложения → scope creep | Фильтрация фидбека через исходные инструкции; явные границы |
| Потеря контекста на handoff | MAST FM-1.4 / FM-2.1; multi-turn −39%, unreliability +112% | Полный трейс для общей работы; для верификации — сознательно **не** передавать |
| Cost blowup | 15× токенов; debate 2,1–3,4×; спавн 50 сабагентов на простой запрос | Effort-scaling таблица в промпте, tool budget, hard caps |
| Недетерминизм | Роутинг выбирает LLM → один вход даёт разные цепочки | Статическая декомпозиция, когда подзадачи известны; логировать трейс |
| Over-parallelization | «В кодинге меньше параллелизуемых задач, чем в research» | Тест: «Если A ошибётся, надо ли переделывать B?» |
| Бесконечный поиск | «endless web searches for nonexistent sources» | Tool budget + критерий насыщения |
| Взаимное отвлечение | Сабагенты забивали канал status-апдейтами | Воркеры не общаются между собой, только вверх дайджестом |
| Смещение источников | Агенты выбирали SEO-контент-фермы вместо академических статей | Иерархия источников прописана в брифе |
| Сикофантия | До 85,5% случаев агент бросает верный ответ ради большинства | Изолированные прогоны + агрегация вместо совещания |
| Менеджер-микроменеджер | Managers «naturally become overly prescriptive» | Менеджер задаёт цель и границы, не метод |
