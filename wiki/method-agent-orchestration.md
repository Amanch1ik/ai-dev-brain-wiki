# Оркестрация агентов

Как дирижировать несколькими LLM-агентами, чтобы это ускоряло работу, а не удваивало счёт и хаос. Практическая надстройка над [[pattern-agent-workflows]]; почему всё ломается — в [[concept-multi-agent-failure-modes]].

## Содержание

### Решающее правило

**Делить по оси «read vs write», а не по оси «сложно / просто».** Формула Cognition после года практики: мультиагентность работает, когда **запись однопоточна, а дополнительные агенты поставляют интеллект, а не действия**.

**Делегируй (веер), когда:**
1. Воркер **read-only** — поиск, чтение, анализ, сбор фактов, ревью.
2. Подзадачи **действительно независимы**. Проверка: *«Если A ошибётся, придётся ли переделывать B?»* Да → не параллелить.
3. Задача **breadth-first** — «найди все X», «сравни N вариантов», «проверь K гипотез».
4. Выход воркера **verbose, а нужен дайджест** — изоляция контекста ради борьбы с context rot.
5. Нужна **чистая перспектива** — ревью, верификация, red-team. Здесь контекст сознательно **не** делится.
6. Нужны **ограничения прав** — воркер с урезанным набором инструментов как security boundary.
7. Ценность задачи окупает **4–15× токенов**.

**Не делегируй, когда:** воркер должен писать в общий артефакт · нужны согласованные неявные решения (стиль, архитектура, нейминг, edge-cases) · частый back-and-forth · фазы делят много контекста · правка мелкая, и оверхед старта воркера съедает выигрыш · критична латентность · **постановка недоспецифицирована — сначала уточни, потом дроби**.

**Гибрид, который реально работает:** последовательный писатель + веер read-only разведчиков **до** записи + веер верификаторов **после**. Writes последовательны, reads параллельны.

### Масштаб усилия

Правила, которые Anthropic вшивает в промпт оркестратора буквально, цифрами — иначе агенты не умеют калибровать усилие (наблюдался спавн **50 субагентов на тривиальный запрос**):

| Класс задачи | Агентов | Tool calls на агента |
|---|---|---|
| Простой факт-финд | 1 | 3–10 |
| Прямое сравнение | 2–4 | 10–15 |
| Сложное исследование | 10+ | с чётко разделёнными зонами |

Практический потолок при ручной работе — **4–8 агентов**: дальше падает не пропускная способность машины, а способность человека помнить, кто что делает. Официальная рекомендация для agent teams — **3–5 воркеров по 5–6 задач**. Настоящее бутылочное горлышко — **ревью, а не запуск**: поднять пять агентов легко, отревьюить пять PR — нет.

### Анатомия брифа воркера

Отсутствие любого поля даёт наблюдаемый режим отказа.

1. **Objective** — одно предложение: что именно должно быть добыто или сделано.
2. **Scope in / out** — явно, что входит и что **не** трогать. Без границ агент «услужливо» выходит за рамки.
3. **Output format** — точная форма возврата. Иначе оркестратор получает несводимые куски.
4. **Источники и инструменты** — иерархия источников обязательна: без неё агенты систематически выбирают SEO-контент-фермы вместо первоисточников.
5. **Tool budget** — сколько вызовов допустимо. Без бюджета — бесконечный поиск несуществующих источников.
6. **Non-overlap statement** — чем твоя доля отличается от долей соседей. Единственная защита от дублирования.
7. **Явный критерий завершения.** Три самых частых режима отказа по MAST — step repetition (15,7%), reasoning-action mismatch (13,2%), unaware of termination conditions (12,4%) — лечатся этим полем и доступом к списку уже сделанного.

Почему расплывчатый бриф катастрофичен: недоспецифицированная постановка даёт **−39%** к результату, причём аптитьюд теряет ~16%, а **нестабильность растёт на ~112%**. Нестабильность **не чинится ретраем** — только переформулировкой.

### Протокол канала

- Воркеры **не общаются между собой** — только вверх, дайджестом на 1–2k токенов. Иначе канал забивается статус-апдейтами.
- Оркестратор **явно разрешает конфликты** между дайджестами, а не склеивает их молча.
- Для **разделяемой** работы передавай полный трейс, а не формулировку задачи. Для **верификации** — наоборот, не передавай ничего: чистый контекст и есть ценность критика.
- Менеджер задаёт **цель и границы, не метод**: без глубокого знания кодовой базы менеджеры естественным образом становятся *overly prescriptive*.

### Верификация

- **Опровергай, а не проверяй.** Воркеру ставится задача «refute X»; находка считается ложной, пока нет конкретного сценария отказа.
- **Гетерогенные линзы вместо N одинаковых судей**: корректность / безопасность / соответствие спеке / регрессии / воспроизводимость. Это sectioning, а не voting.
- **Гомогенная панель, которая совещается, — антипаттерн.** Дебаты одинаковых агентов стоят 2,1–3,4× токенов, дают сикофантию до 85,5% и теряют правильный ответ, который был в пуле. Изолированные прогоны с агрегацией дешевле и надёжнее.
- **Evaluator-optimizer** применять только при формулируемых критериях, с hard cap на итерации и фильтрацией фидбека генератором через исходные инструкции пользователя — иначе scope creep и бесконечный цикл.
- **Loop-until-dry** — повторять цикл discovery, пока итерация не перестаёт приносить **новые** находки. Критерий остановки формулировать измеримо: «две подряд итерации без новых уникальных фактов».

### Восемь принципов промптинга оркестратора (Anthropic)

1. **Think like your agents** — прогони поведение воркера мысленно по шагам, чтобы увидеть режимы отказа.
2. **Teach the orchestrator how to delegate** — детальные брифы, иначе дубли и дыры.
3. **Scale effort to query complexity** — правила масштабирования цифрами в промпте.
4. **Tool design and selection are critical** — явные эвристики выбора инструмента.
5. **Let agents improve themselves** — модель сама диагностирует провалы и переписывает описания инструментов; агент, итерировавший описания, дал **−40% времени** выполнения.
6. **Start wide, then narrow down** — агенты склонны сразу выдавать длинные узкие запросы, которые ничего не находят.
7. **Guide the thinking process** — extended thinking как управляемый scratchpad для планирования, interleaved thinking у воркеров для адаптации.
8. **Parallel tool calling transforms speed** — 3–5 воркеров параллельно, каждый с 3+ одновременными инструментами; на сложных запросах даёт **до −90% времени**.

### Прод-инженерия оркестра

- **Statefulness и накопление ошибок**: агенты живут долго и держат состояние — нужен durable execution и восстановление; мелкий сбой без митигации катастрофичен.
- **Rainbow deployments**: плавный перевод трафика на новую версию, чтобы не рвать работающих агентов.
- **Отладка**: недетерминизм между прогонами даже на идентичных промптах → нужен полный трейсинг, а не логи по факту падения.
- **Оценка**: старт с ~20 запросов для быстрой итерации, LLM-as-judge с рубрикой (accuracy, citations, completeness, source quality, tool efficiency), плюс обязательное человеческое тестирование краевых случаев.

### Чек-лист дирижёра

**Перед декомпозицией:** постановка специфицирована? · read или write? · тест независимости пройден? · окупает ли ценность 4–15× токенов?

**Выбор формы:** подзадачи известны заранее → статическая параллелизация, а не динамический оркестратор · нужна когерентность артефакта → один писатель + read-воркеры · нужна проверка → асимметричный критик с чистым контекстом · есть чёткие критерии → evaluator-optimizer с hard cap.

**Каждый бриф:** Objective · Scope in/out · Output format · Источники · Tool budget · Non-overlap · Критерий завершения.

**Возврат:** дайджест, не сырьё · воркеры не общаются между собой · конфликты разрешаются явно · **отдельный шаг сведения** — без него теряется половина пользы.
